1. What are basic OO Heuristics?
-Keep related data and behavior in one place
-A class should capture only 1 abstraction
-beware of classes with many accessors in their public interface
2. What are bad smells?
-comments should explain why, not what
-incommunicative name
-inconsistent names
-type embedded in name
-conditional complexity: consider decorator, strategy, or state.
-dead code
-utility methods: related code should be together
3. What is the one responsibility rule?
-A class does it all, well, and only.
-Class should be described in 25 words

13. Long functions/large class: 
-The longer a function is, the harder to understand. 
-Small functions named with intention, extract function, replace temp with query, introduce parameter object, preserve whole object, replace function with command?,  
14. Long parameter lists: 
-Pass the containing object if possible or combine functions into a class.
-Replace parameter with query, preserve whole object, introduce parameter object, remove flag argument.
15. Global data: 
-Can be modified from anywhere in code, hard to find bugs. Includes class variables and singletons.
-encapsulate variable (function wrapper allows seeing what changed the variable), make immutable, 
16. mutable data:
-unexpected consequences when used by multiple readers.
-encapsulate variable,split variable, slide statements, extract function, separate query from modifier, remove setting method, replace derived variable with query, combine functions into class, combine functions into transform, change reference to value.
17. divergent change:
-module changed in different ways for different reasons.
-changes to class involve many parts, means too much functionality, split into another class.


18. shotgun surgery:
-A change requires many small dispersed changes, cascaded in many classes.
-move function, move field, combine functions into class, combine functions into transform, split phase, inline function, inline class.

39. What is refactoring?
Changing internal structure/observable behavior of software.
To make software easier to understand/modify.
40. When to refactor?
Rule of three
-add function
-fix bug
-code review


41. When is refactoring hard?
-databases
-changing public interfaces
-major design issues


42. What is Johnson’s law?
-If it is not tested it does not work.
-the more time between coding and testing:
-more effort to write tests
-more effort to find bugs
-fewer bugs are found
-time wasted working with buggy code
-increased development time
-decreased quality


43. What are unit tests?
-test individual code segments
-automated


44. When to write tests?
-write test, then code:
-saves time, makes interface and functionality clear, removes temptation to skip


45. What to test?
-Everything that could break
-test values: inside, outside, on boundary of valid range
-GUIs are very hard to test: keep gui layer thin, test program behind gui, not gui
